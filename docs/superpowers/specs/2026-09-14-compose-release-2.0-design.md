# neops-docker-compose 2.0 — design

Status: approved 2026-09-14 after the design-challenge round. Branch `release/2.0`.

## Goal

A production docker-compose deployment of the NeOps 2.0 stack (neops-core, neops-workflow-engine, monitor app, neops-worker-sdk, neops-web-client) that an operator installs with one command after filling in `.env`, that supports the deployment scenarios we ship to customers as selectable overlays, that keeps every byte of durable state in bind-mounted directories, and that can be changed later without friction through versioned deployment migrations.

Decisions already taken with the user:

| Topic | Decision |
|---|---|
| Relation to the 1.0 layout | Clean rewrite. `release/2.0` deletes `neops/`, `traefik/`, `keycloak/`, `secure-gw/`, `kea/`, `.support/`. 1.0 stays on `develop`/`main`. |
| Public routing | Both models as overlays: one hostname per service (default) and a single shared hostname with path routing. |
| Postgres | One Postgres container per service (`postgres-cms`, `postgres-engine`, `postgres-keycloak`). |
| Operator CLI | Python, uv-managed project, `./neops` wrapper. |
| Image versions | The repo pins a tested set; `.env` overrides are for emergencies only. |
| Migrations | Deployment-layout migrations run by the CLI; app DB migrations stay inside the containers. |
| Metrics | Ported as an optional overlay. |
| Keycloak | Bundled overlay with auto-provisioned realm and client, own Postgres. |
| Worker | In the base stack, base function blocks only, no bind mount for custom blocks (customers deploy an extra worker). |
| TLS | Operator-provided PEM files, Let's Encrypt (HTTP-01), and self-signed generated by the CLI. |
| Traefik off | Services published on `127.0.0.1` for an external proxy on the same host. |

Out of scope for this release: secure-gateway, storage, pgbouncer overlay, a `.env` wizard, automated restore, data migration from a 1.0 installation.

## Facts the design depends on

Verified in the sibling repos (charts, Dockerfiles, settings, git tags) on 2026-09-14. Two reviewer agents re-verified them; corrections from that round are marked ⟲.

- **neops-core** runs four workloads from one image: web (`uvicorn --workers 4 neopsapp.asgi:application`), Celery worker, Celery beat, and a one-shot migrate step. The chart runs `/app/backend/init.sh` (wait for DB and Elasticsearch, `manage.py migrate`, `manage.py elastic_index --create`) and then an idempotent `get_or_create` superuser. ⟲ `init.sh` has a `$?` re-read bug that makes it **exit 1 on the success path of a fresh database** (the chart hides it behind `backoffLimit: 10`, and the script exists only in the enterprise image), so `cms-init` runs the three steps itself instead of calling the script. The image's `ENTRYPOINT` is `/docker-entrypoint.sh`, which installs `/cust-cert` CAs and then execs the command; every core service keeps that entrypoint and sets only `command`. Only the enterprise image `quay.io/zebbra/neops-core` ships `neops_cron`, `neops_auth_allauth` and `neops_reports`; `neops-cms-free`/`neops-cms` cannot be swapped in. `DJANGO_STATIC_URL=/djstatic/` is baked into the image, static files are served by WhiteNoise. `DATABASE_URL`, `REDIS_URL`, `ELASTICSEARCH_HOSTS`, `DJANGO_SECRET_KEY`, `NEOPS_PLUGINS` are the load-bearing variables. `DJANGO_ALLOWED_HOSTS` is a plain list with no default, so it must contain every Host header core will see, including in-network ones. `CORS_ORIGIN_ALLOW_ALL` is the only CORS knob core has (no allow-list setting exists; ⟲ the corsheaders middleware is also ordered last, a core defect); ⟲ it casts booleans correctly (`False`, `false`, `0` all resolve to off, verified in the image). Core also has no health route, no `SESSION`-free probe path, and stock Postgres `max_connections=100` is known to run dry under a single core web process (about 90 idle persistent connections) — measured in the KIND deployment and fixed there with 300. `CSRF_TRUSTED_ORIGINS` is not read. Custom CAs dropped into `/cust-cert` are installed by the entrypoint. Health: `GET /admin/login/`. Tag `2.1.0-beta.5` carries all of this (allauth, `NEOPS_PUBLIC_URL`, JWT keys); nothing on `develop` past the tag touches it.
- **Core's root-absolute URL prefixes** (from `neopsapp/urls.py` and the webhook plugin): `/graphql`, `/graphiql`, `/admin`, `/djstatic`, `/.well-known`, `/accounts`, `/auth/oidc-login`, `/auth/oidc-complete`, `/auth/oidc-logout`, `/webhook`. Everything else falls into an SPA catch-all that returns core's own `index.html`. ⟲ `STATIC_URL` is absolute, and Django does not prepend a script prefix to absolute static URLs, so core cannot be served under a path prefix without a rewriting shim. Shared-hostname mode therefore routes these prefixes to core on the web client's hostname (the model 1.0 production used) instead of mounting core under `/cms`.
- **OIDC in core** is the `neops_auth_allauth` plugin: providers seeded insert-only from the JSON at `AUTH_PROVIDERS_CONFIG_PATH` (`{"providers":[{provider_id, name, client_id, secret, settings.server_url}]}`), RS256 keypair via `NEOPS_JWT_PRIVATE_KEY_PATH`/`NEOPS_JWT_PUBLIC_KEY_PATH`, and `NEOPS_PUBLIC_URL`, `NEOPS_FRONTEND_CALLBACK_URL`, `NEOPS_FRONTEND_LOGIN_URL`, `RATELIMIT_IP_META_KEY`, `REDIS_URL` required behind a proxy. Local login is disabled while allauth is active. ⟲ The old `OIDC_CONFIG_PATH` file is legacy-frontend compatibility only: web-client 5.0.0 reads providers from `appSettings.oidcProviders` and never references `oidc-config.json`, and core fails soft when the file is missing, so no noop file is shipped. The web client owns `/auth/callback` and `/login`; core owns `/auth/oidc-*`, so the two coexist on one hostname. Rotating `DJANGO_SECRET_KEY` invalidates every static API key (they are `Signer`-signed with it), so the engine's CMS token must be re-minted afterwards. `generate_api_key` inserts a new key row on every call and never revokes one; the superuser password is set only on creation; a Postgres password is honoured only at initdb.
- **neops-workflow-engine** ⟲ serves its **worker API unauthenticated by design**: `POST /blackboard/job` (returns job context including plaintext device credentials), `POST /blackboard/job/result`, `/workers/register`, `/workers/:uuid/unregister`, `/function-blocks/register` are `@Public()` and are not covered by `NEOPS_AUTHZ_MODE`. The engine assumes a private network for the worker half, while the monitor app needs the rest of the API from the browser. The public route must therefore be an allow-list. Leave `NEOPS_VERSION` unset (setting it to the tag makes `/version` reject a matching client). It runs its MikroORM migrations on boot, takes a single-instance advisory lock (never scale it, prefer stop-then-start), refuses to boot with the placeholder `NEOPS_CMS_TOKEN` unless `NODE_ENV=development`, refuses to boot without a JWT verification key unless `NEOPS_AUTHZ_MODE=disabled`, ignores `POSTGRES_USER` (connects as `postgres`), hardcodes database `neops-workflow`, ⟲ and defaults `POSTGRES_HOST=localhost`, `POSTGRES_PORT=5434`, so all three Postgres variables must be set. Health: `GET /health`. CORS: `NEOPS_CORS_ORIGINS`, comma-separated exact origins. Tag `0.43.0-beta.2` carries the auth-boot and refusal logic.
- **neops-monitor-app** is an nginx image on port 80 configured at start from `ENGINE_BASE_URL` and `WEBCLIENT_ORIGIN` (validated: http(s), conservative charset, else the container exits). ⟲ It must run on a different origin than the web client: the **web client** compares the two origins and disables the whole workflow-manager feature when they match. ⟲ **No tag exists on Quay**: the engine's `publish-monitor-image` job fails with `npm error 401` because it builds the monitor Dockerfile without the `npm_token` build secret its `client-gen` stage mounts. Fixing that job in `neops-workflow-engine/.github/workflows/release-on-tag.yml` and re-tagging the engine is a **release dependency** of this repo. Until then the pin is unpullable and tests use a locally built image.
- **neops-worker-sdk** needs `URL_BLACKBOARD`, `DIR_FUNCTION_BLOCKS=neops/fb`, `WORKER_NAME`. Worker routes on the engine are public; no credential. ⟲ The image at `0.2.0-beta.5` registers 22 base function blocks (not 25).
- **neops-web-client** is nginx-unprivileged on 8080; every `FRONTEND_*` variable is written verbatim into a JS literal (plain URLs only). Variables: `FRONTEND_GRAPHQL_ENDPOINT`, `FRONTEND_WORKFLOW_MANAGER_URL`, `FRONTEND_DEVMODE` (⟲ `FRONTEND_FILEAPI_ENDPOINT` has no runtime consumer; set for compatibility only). A quote or space in a value breaks the injected JS silently, so `check` validates them as plain URLs. ⟲ No shipped frontend opens a WebSocket (the client library polls), so WS passthrough matters only for graphiql and third-party clients.
- **CMS API key for the engine** is minted with `manage.py generate_api_key <user_pk> workflow` (last stdout line), which needs a running CMS with the superuser present. Bring-up is therefore two-phase.
- **Keycloak 26.5**: `start --import-realm` imports `/opt/keycloak/data/import/*.json` on first start only (⟲ plain `start` re-augments on every boot, 30–60 s); behind a proxy it needs `KC_HTTP_ENABLED=true`, `KC_PROXY_HEADERS=xforwarded`, `KC_HOSTNAME=<public URL>`; `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true` lets the CMS use the in-network URL while `iss` stays public; ⟲ the management endpoints on port 9000 move with `KC_HTTP_RELATIVE_PATH` unless `KC_HTTP_MANAGEMENT_RELATIVE_PATH=/` is set; the image has no curl, the documented healthcheck uses bash's `/dev/tcp`. Core ships a realm export whose `neops-auth` client carries the client-roles mapper that puts `resource_access` into the ID token and userinfo, which role sync requires.
- **Elasticsearch 8.9.2** official image runs as uid 1000 and ⟲ does not chown its data directory (`TAKE_FILE_OWNERSHIP` is a Bitnami-only variable), so the bind mount must be owned by 1000 before first start. ⟲ It refuses to start with `vm.max_map_count` below 262144 (stock Linux: 65530) and flips indices read-only at the 95 % disk flood stage.
- **Compose 5.4** (verified here): `up --wait` accepts a one-shot that exited 0 *because* another service depends on it with `service_completed_successfully`, and re-runs it on every `up`; `environment` merges by key across overlays even between list and map form; `depends_on` and `ports` merge, `command` is replaced; `env_file` values reach the container only and are never available for `${}` interpolation; `COMPOSE_FILE` relative paths resolve against the caller's cwd, not `--project-directory`.
- **Traefik v3.6** (verified against source): sets `X-Real-Ip` to the client address and deletes untrusted inbound copies, so `RATELIMIT_IP_META_KEY=HTTP_X_REAL_IP` is correct behind it (⟲ and only behind it: django-ratelimit raises per request when the configured header is absent, turning every login into a 500 behind a proxy that does not set it); ACME HTTP-01 needs the `web` entrypoint reachable on port 80; the file provider supports Go templating; with only `tls.certificates` and no default certificate, non-SNI and unmatched requests get Traefik's built-in self-signed cert.
- **Images on Quay** (2026-09-14): `neops-core 2.1.0-beta.5`, `neops-workflow-engine 0.43.0-beta.2`, `neops-worker-sdk 0.2.0-beta.5`, `neops-web-client 5.0.0`, `traefik v3.6.25`, `keycloak 26.5.2`, `postgres 16-alpine`, `redis 7-alpine`, `elasticsearch 8.9.2`, `grafana 11.5.2` all resolve. `neops-monitor-app` does not (see above).
- **This dev box** has ports 80 and 443 taken by the shared KIND cluster, so every published port is configurable (`NEOPS_HTTP_PORT`, `NEOPS_HTTPS_PORT`, `NEOPS_MONITOR_PORT`, and the expose-mode ports).

## Services (`compose.yaml`)

All services share the default network; the base file publishes no ports. `restart: unless-stopped` everywhere except one-shots. Image references come from a single `x-versions` block at the top of the file (verified to render correctly):

```yaml
x-versions:
  core: &core-image quay.io/zebbra/neops-core:${NEOPS_CORE_TAG:-2.1.0-beta.5}
  engine: &engine-image quay.io/zebbra/neops-workflow-engine:${NEOPS_ENGINE_TAG:-0.43.0-beta.2}
  monitor: &monitor-image quay.io/zebbra/neops-monitor-app:${NEOPS_MONITOR_TAG:-0.43.0-beta.2}
  worker: &worker-image quay.io/zebbra/neops-worker-sdk:${NEOPS_WORKER_TAG:-0.2.0-beta.5}
  web: &web-image quay.io/zebbra/neops-web-client:${NEOPS_WEB_TAG:-5.0.0}
```

Every service carries a `logging:` block (`json-file`, `max-size: 20m`, `max-file: 5`) so an unrotated log cannot fill the disk. Sentry, email, retention and Nornir knobs are passed through from `.env` with the same names as in 1.0 and empty defaults.

### Generated per-service env files (container-only, never interpolated)

Compose cannot parse a URL, so the CLI renders the derived values. They are consumed only through `env_file:` and are never referenced with `${}` in a compose file (Compose does not interpolate from `env_file`). Nothing in a compose `command:` depends on them.

- `generated/cms.env`: `DJANGO_ALLOWED_HOSTS=<hostnames of NEOPS_CMS_URL and NEOPS_WEB_URL>,cms,localhost,127.0.0.1` (`cms` because the engine calls `http://cms:8000`, the loopback names for the healthcheck; never `*`); `CORS_ORIGIN_ALLOW_ALL=True` only when the origin of `NEOPS_WEB_URL` differs from the origin of `NEOPS_CMS_URL` (hosts mode and expose mode; omitted in shared-host mode where both are one origin; the SPA authenticates with Bearer tokens, not cookies, so allow-all CORS exposes nothing cookie-authenticated, and core offers no per-origin list); `ACCOUNT_DEFAULT_HTTP_PROTOCOL` from the scheme of `NEOPS_WEB_URL`.
- `generated/keycloak.env`: `KC_HTTP_RELATIVE_PATH` from the path of `NEOPS_KEYCLOAK_URL` (`/` when none).
- `generated/monitor.env`: nothing today; reserved so the monitor's derived values have a home without a compose change.

## Durable state

Everything durable lives under `${NEOPS_DATA_DIR:-./data}` as bind mounts. No named volume anywhere in any compose file; a unit test parses every compose file and enforces it.

```
data/
├── cms/postgres/          Postgres data dir (postgres-cms)
├── cms/media/             Django MEDIA_ROOT (/app/backend/media)
├── cms/tmp/               core /tmp (scratch, report generation)
├── engine/postgres/       Postgres data dir (postgres-engine)
├── keycloak/postgres/     Postgres data dir (postgres-keycloak)      [keycloak overlay]
├── elasticsearch/         ES data, uid 1000 (rebuildable with elastic_index --populate, but slow)
├── traefik/acme/          acme.json                                    [tls-acme overlay]
├── metrics/victoria/  metrics/grafana/                                 [metrics overlay]
├── secrets/               mode 0700; contents 0600
│   ├── jwt/private.pem  jwt/public.pem     RSA-2048, PKCS#8 / SPKI (CMS signs, engine verifies)
│   ├── engine.env                          NEOPS_CMS_TOKEN=<api key>
│   ├── keycloak-client.env                 NEOPS_KEYCLOAK_CLIENT_SECRET=<random>   [keycloak overlay]
│   └── tls/cert.pem  tls/key.pem  tls/ca.pem   self-signed                         [when NEOPS_TLS_SELF_SIGNED=true]
└── .neops/state.json      applied migrations + install metadata
```

Rule stated in the README: **everything the deployment needs to be rebuilt is `.env` plus `data/`** (plus `certs/` and `cust-cert/` when used). `docker system prune -a --volumes` loses nothing; `./neops up` recreates every container from those. A file-level copy of `data/` is only a valid backup **with the stack stopped**; while it runs, `./neops backup` (logical dumps) is the only sanctioned path. Redis is the only stateful service without a directory, on purpose: it holds cache and queued Celery tasks (unclaimed tasks are lost on a wipe, nothing else), and core requires it as the shared cache when allauth is active. Elasticsearch is derived data and is not backed up; a restore ends with `manage.py elastic_index --create` and `--populate`.

## Public URLs and scenarios

`.env` declares the browser-facing URL of each entry point. Compose files interpolate them directly; the CLI derives the rest (hostnames, Traefik routers, per-service env files).

```
NEOPS_WEB_URL=https://neops.example.com
NEOPS_CMS_URL=https://cms.neops.example.com
NEOPS_ENGINE_URL=https://engine.neops.example.com
NEOPS_WORKFLOWS_URL=https://workflows.neops.example.com
NEOPS_KEYCLOAK_URL=https://auth.neops.example.com      # keycloak overlay only
NEOPS_GRAFANA_URL=https://grafana.neops.example.com    # metrics overlay only
```

Shared-hostname variant of the same keys (`compose.traefik-shared-host.yaml`):

```
NEOPS_WEB_URL=https://neops.example.com
NEOPS_CMS_URL=https://neops.example.com                # same origin as the web client, no path
NEOPS_ENGINE_URL=https://neops.example.com/engine
NEOPS_WORKFLOWS_URL=https://neops.example.com:8443     # distinct origin; port = NEOPS_MONITOR_PORT
NEOPS_KEYCLOAK_URL=https://neops.example.com/sso       # any path that is not a core or web-client prefix
NEOPS_GRAFANA_URL=https://neops.example.com/grafana
```

URL rules enforced by `./neops check`: `NEOPS_CMS_URL` never has a path (core cannot live under a prefix); it is either its own origin (hosts mode) or exactly `NEOPS_WEB_URL` (shared-host mode, requires the shared-host overlay); `NEOPS_WORKFLOWS_URL` is an origin distinct from `NEOPS_WEB_URL`; `NEOPS_ENGINE_URL`, `NEOPS_KEYCLOAK_URL`, `NEOPS_GRAFANA_URL` may carry a path, which must not start with a core prefix or with `/auth`, `/login`; every URL is http(s) with a hostname and nothing else (no query, no userinfo, no characters outside the monitor app's allowed set).

`COMPOSE_FILE` in `.env` selects the scenario (`COMPOSE_PATH_SEPARATOR=:`). The shipped examples:

| `examples/` | `COMPOSE_FILE` | Notes |
|---|---|---|
| `external-proxy.env` | `compose.yaml:compose.expose.yaml` | ports on `127.0.0.1`: web 8080, cms 8000, engine 3030, monitor 3031 (`NEOPS_*_PORT`, `NEOPS_BIND_ADDRESS`); the external proxy must **overwrite** `X-Real-IP` and `X-Forwarded-Proto` |
| `traefik-http.env` | `compose.yaml:compose.traefik.yaml` | plain HTTP on :80, evaluation only |
| `traefik-tls-files.env` | `…:compose.traefik.yaml:compose.tls-files.yaml` | `NEOPS_TLS_CERT_FILE=./certs/cert.pem`, `NEOPS_TLS_KEY_FILE=./certs/key.pem`; HTTP→HTTPS redirect |
| `traefik-tls-selfsigned.env` | same as above | `NEOPS_TLS_SELF_SIGNED=true`, files under `data/secrets/tls/`, minted by `./neops keys` with SANs for every hostname in the URLs |
| `traefik-acme.env` | `…:compose.traefik.yaml:compose.tls-acme.yaml` | `NEOPS_ACME_EMAIL`; HTTP-01 on :80; `acme.json` in `data/traefik/acme` |
| `traefik-shared-host-tls-files.env` | `…:compose.traefik.yaml:compose.traefik-shared-host.yaml:compose.tls-files.yaml` | single hostname; adds the `NEOPS_MONITOR_PORT` entrypoint for the monitor origin |
| `oidc-external.env` | `traefik-tls-files` + `compose.oidc.yaml` | `NEOPS_OIDC_PROVIDER_ID`, `NEOPS_OIDC_NAME`, `NEOPS_OIDC_CLIENT_ID`, `NEOPS_OIDC_CLIENT_SECRET`, `NEOPS_OIDC_DISCOVERY_URL` |
| `oidc-keycloak.env` | `traefik-tls-files` + `compose.oidc.yaml:compose.keycloak.yaml` | `NEOPS_KEYCLOAK_URL`, `NEOPS_KEYCLOAK_ADMIN_PASSWORD`, `NEOPS_KEYCLOAK_DB_PASSWORD` |
| `metrics.env` | `traefik-tls-files` + `compose.metrics.yaml` | `NEOPS_GRAFANA_URL`, `NEOPS_GRAFANA_ADMIN_PASSWORD` |

Overlays compose freely (`oidc-keycloak` with `tls-acme`, `metrics` with `external-proxy`, ...). `./neops check` validates the combination: every file in `COMPOSE_FILE` exists; exactly one of `expose`/`traefik`; at most one `tls-*`, and only with `traefik`; `shared-host` only with `traefik`; `keycloak` requires `oidc`; `tls-acme` requires `NEOPS_HTTP_PORT=80` (HTTP-01 has no other port); the URL rules above; required keys per overlay are non-empty; tracked compose files are unmodified (local changes belong in `compose.override.yaml`).

### Routing overlays

`compose.traefik.yaml` runs `traefik:v3.6.25` with the **file provider only** (no Docker socket), a fixed command (`--configFile=/etc/traefik/traefik.yml`), host ports `${NEOPS_HTTP_PORT:-80}:80` and `${NEOPS_HTTPS_PORT:-443}:443`, dashboard off, access log on. Both Traefik files are rendered by the CLI from the public URLs, so overlays never have to restate the command:

- `generated/traefik/traefik.yml` (static): entrypoints `web` (:80) and `websecure` (:443); `monitor` (:8443 in-container, host `${NEOPS_MONITOR_PORT:-8443}`) only in shared-host mode; the ACME resolver only in acme mode; HTTP→HTTPS redirection on `web` whenever TLS is on (the ACME challenge path is exempted by Traefik itself).
- `generated/traefik/dynamic.yml`: each URL → `(host, path, port)`; entrypoint by scheme and port; router rule `Host(\`h\`)` plus `PathPrefix(\`p\`)` when the URL has a path, priority by rule length; `StripPrefix` for engine, keycloak-free paths and grafana when they carry one (Keycloak keeps its prefix, it serves it natively via `KC_HTTP_RELATIVE_PATH`); services point at compose DNS names (`http://web:8080`, `http://cms:8000`, `http://engine:3030`, `http://monitor:80`, `http://keycloak:8080`, `http://grafana:3000`); TLS: `tls.certificates` **and** `tls.stores.default.defaultCertificate` from `/etc/traefik/certs/{cert,key}.pem` (tls-files) or `certResolver: letsencrypt` on every https router (tls-acme).
- **The engine is exposed through an allow-list**, never as a catch-all: routers for the prefixes the monitor app and operators need (`/workflow-definition`, `/workflow-execution`, `/schema`, `/license`, `/me`, `/version`, `/health`, `/api` docs) and one higher-priority router for `/blackboard`, `/workers`, `/function-blocks` that ends in an `ipAllowList` middleware with an unroutable range (TEST-NET), which Traefik answers with 403. The worker talks to `http://engine:3030` on the compose network and never uses the public route. The prefix lists live in `neops_compose/routes.py` next to the core ones.
- `compose.traefik.yaml` sets `RATELIMIT_IP_META_KEY=HTTP_X_REAL_IP` on the core services, because Traefik is known to set and overwrite that header.
- Shared-host mode adds, on the web client's hostname and above the web catch-all, one router per core prefix (`/graphql`, `/graphiql`, `/admin`, `/djstatic`, `/.well-known`, `/accounts`, `/auth/oidc-login`, `/auth/oidc-complete`, `/auth/oidc-logout`, `/webhook`) to `cms`, unstripped. The list lives in one place, `neops_compose/routes.py`, with a comment naming `neopsapp/urls.py` as its source; adding a core URL prefix is a two-repo change. The monitor is served at the root of the `monitor` entrypoint.

`compose.expose.yaml` publishes `${NEOPS_BIND_ADDRESS:-127.0.0.1}:${NEOPS_WEB_PORT:-8080}:8080` and the equivalents for cms, engine, monitor, keycloak and grafana. The README and `examples/external-proxy.env` document the proxy contract: route by hostname (or the shared-host prefix list); **deny** `/blackboard`, `/workers`, `/function-blocks` on the engine hostname; **overwrite** `X-Forwarded-Proto` (core hardcodes `SECURE_PROXY_SSL_HEADER`); a body-size limit of at least 200 MB on the CMS. `RATELIMIT_IP_META_KEY` ships commented out in that example with the header requirement beside it, because a proxy that does not set `X-Real-IP` turns every login into a 500, and one that appends instead of overwriting lets a client rotate the header and bypass every per-IP limit. `./neops doctor` sends a forged `X-Real-IP` through the public CMS URL and reports whether it reaches core unchanged, and posts a deliberately bad login expecting 400/429, never 500.

### Auth overlays

`compose.oidc.yaml`: sets `NEOPS_PLUGINS=neops_cron neops_auth_static_api_key neops_auth_allauth neops_permissions_simple neops_reports` on the four core services, mounts `generated/providers.json` at `/etc/neops/providers.json` with `AUTH_PROVIDERS_CONFIG_PATH`, sets `NEOPS_FRONTEND_CALLBACK_URL=${NEOPS_WEB_URL}/auth/callback`, `NEOPS_FRONTEND_LOGIN_URL=${NEOPS_WEB_URL}/login`. `providers.json` is rendered from `NEOPS_OIDC_*`.

`compose.keycloak.yaml`: `postgres-keycloak` (`postgres:16-alpine`, `data/keycloak/postgres`) and `keycloak` (`quay.io/keycloak/keycloak:26.5.2`, `start --import-realm`, `KC_DB=postgres`, `KC_DB_URL=jdbc:postgresql://postgres-keycloak:5432/keycloak`, `KC_HOSTNAME=${NEOPS_KEYCLOAK_URL}`, `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`, `KC_HTTP_ENABLED=true`, `KC_PROXY_HEADERS=xforwarded`, `KC_HEALTH_ENABLED=true`, `KC_HTTP_MANAGEMENT_RELATIVE_PATH=/`, `KC_BOOTSTRAP_ADMIN_USERNAME/PASSWORD`, `env_file: generated/keycloak.env`; healthcheck `(printf 'HEAD /health/ready HTTP/1.0\r\n\r\n' >&0; grep 'HTTP/1.0 200';) 0<>/dev/tcp/localhost/9000` with a 120 s start period). It mounts `generated/keycloak/realm.json` at `/opt/keycloak/data/import/neops-realm.json`: realm `neops`, confidential client `neops-auth` with the client secret from `data/secrets/keycloak-client.env`, redirect URI `${NEOPS_CMS_URL}/accounts/oidc/keycloak/login/callback/`, post-logout redirect `${NEOPS_WEB_URL}/*`, the client-roles mapper (`resource_access.${client_id}.roles` into ID token and userinfo), no users. It overrides the provider seed values so `providers.json` points at `http://keycloak:8080<KC_HTTP_RELATIVE_PATH>/realms/neops/.well-known/openid-configuration`. Keycloak imports the realm only on first start; later realm changes are made in the admin console (or by deleting `data/keycloak` deliberately). Operators create users and assign the `neops-auth` client roles in Keycloak.

### Metrics overlay

`compose.metrics.yaml` ports the 1.0 stack: `celery-exporter` (redis broker), `redis-exporter`, `postgres-exporter-cms`, `postgres-exporter-engine`, `elasticsearch-exporter`, `victoriametrics` (`data/metrics/victoria`, 30 d retention), `vmalert` (rules from `metrics/vmalert/rules`), `grafana` (`data/metrics/grafana`, provisioning from `metrics/grafana`, admin password from `.env`). Only Grafana is routed publicly (`NEOPS_GRAFANA_URL`) and only when set.

## The `./neops` CLI

uv project, `requires-python >= 3.12`, `[project.scripts] neops = "neops_compose.cli:main"`. The wrapper makes `./neops <cmd>` work from a fresh clone with only `uv` and `docker` installed. argparse, no CLI framework. Modules, one concern each:

| Module | Responsibility |
|---|---|
| `cli.py` | argparse wiring; every subcommand delegates to one function |
| `env.py` | read `.env` (python-dotenv), typed accessors, required-key rules per overlay, URL parsing (`PublicUrl(scheme, host, port, path)`) |
| `scenario.py` | the overlay model: which files are in `COMPOSE_FILE`, consistency rules used by `check` |
| `routes.py` | the core URL prefixes routed in shared-host mode, and the reserved web-client paths |
| `compose.py` | subprocess wrapper around `docker compose`; **always runs with cwd = repo root** (relative `COMPOSE_FILE` entries resolve against the cwd), `up --wait`, `exec`, `ps --format json` |
| `render.py` | jinja2 rendering of `generated/` from env + scenario; deterministic output, `--diff` flag |
| `secrets.py` | RSA keypair, self-signed CA + server cert (SANs from URLs), random client secret; idempotent, 0600; `keys` compares an existing self-signed cert's SANs with the URLs and refuses to proceed with a stale one unless rotated |
| `token.py` | idempotent: if `data/secrets/engine.env` exists and the key still authenticates against the CMS, do nothing; otherwise mint via `compose exec cms manage.py generate_api_key`, record the issued row id in `state.json`, write the env file, then `up -d --force-recreate engine` explicitly. Rotation deletes the previously issued row. |
| `rotate.py` | the sanctioned secret rotations, each doing the whole job: `db-password <cms|engine|keycloak>` (`ALTER ROLE` in the container, then rewrite `.env`), `admin-password` (`manage.py changepassword`, then rewrite `.env`), `secret-key` (rewrite `.env`, restart core, then re-mint the engine token), `jwt` (new keypair, restart cms and engine; all sessions end), `tls` (self-signed only), `token`, `keycloak-client` |
| `migrate.py` | discover `migrations/NNNN_*.py`, state file, `apply`, `--dry-run`, `--fake` |
| `doctor.py` | container health, HTTP checks through the public URLs (with `--connect 127.0.0.1` to test on a box without DNS), the forged `X-Real-IP` probe, engine worker registration |
| `backup.py` | `pg_dump` per Postgres into `backups/<ts>/`, copy `.env` and `data/secrets` |
| `preflight.py` | docker/compose versions, ports free, disk space, `vm.max_map_count` (fails with the exact `sysctl -w` line), Quay login, `.env` completeness and URL rules, every pinned image manifest resolvable (so a missing upstream tag fails here with a clear message, not mid-pull), the `.env` DB passwords still accepted by a running Postgres (so a stale rotation names itself instead of looking like data loss) |
| `state.py` | `data/.neops/state.json`: applied and faked migrations, issued API key ids, the image tag set of the last successful `up`, the CLI version that wrote it |

Commands:

| Command | Behaviour |
|---|---|
| `./neops install` | `check` → `migrate` → `keys` → `render` → `pull` → `up -d --wait` for `cms` and its dependencies → `token` → `up -d --wait` (all) → `doctor`. Idempotent: a second run changes nothing and reports the state. |
| `./neops up` | `migrate` → `render` → `pull` → `up -d --wait` (always the full service set, so the one-shot's dependency edge exists) → `doctor` → record the tag set in `state.json`. Refuses when the pinned core tag is older than the last successful set unless `--allow-downgrade` (Django migrations are not reversible; downgrade means restore). The command after every `git pull` or `.env` edit. |
| `./neops down [--all]` | `compose down` (`--all` also stops the one-shots; never `-v`) |
| `./neops purge` | `down`, then removes `data/` and `generated/` after an interactive confirmation that repeats the data path; the only sanctioned way to wipe an installation |
| `./neops rotate <what>` | see `rotate.py`; each prints what will be invalidated (sessions, the engine token) before acting |
| `./neops restart <svc>` / `ps` / `logs` / `compose -- <args>` | pass-throughs with the scenario's `COMPOSE_FILE` |
| `./neops check` | preflight + scenario validation; exits non-zero with one actionable message per problem |
| `./neops migrate [--dry-run] [--fake <full name>]` | apply pending migrations in order; `--fake` takes the full migration name, prints what it skips, asks for confirmation, and is recorded as faked so `status` and `doctor` flag the hand-patched state |
| `./neops keys` | JWT keypair, TLS self-signed (when enabled), Keycloak client secret; never overwrites, rotation only via `rotate` |
| `./neops token` | mint the engine's CMS API key when missing or no longer valid, and recreate the engine; rotation via `rotate token` |
| `./neops render [--diff]` | regenerate `generated/`; `--diff` prints what would change |
| `./neops doctor` | health report, non-zero on any failure; output redacted by construction so it can be pasted into a ticket (`compose -- config` is not: it prints every secret) |
| `./neops status` | pinned vs running image tags, last-known-good tag set, pending and faked migrations, scenario summary; redacted |
| `./neops backup [--dir DIR] [--keep N]` | self-contained archive: `pg_dump` per database, `.env`, `data/secrets`, `certs/`, `cust-cert/`, and a manifest of image tags and applied migrations; 0600; `--keep` prunes old archives. Restore is documented step by step in the README and ends with `elastic_index --create` and `--populate`. |

`generated/` is rebuilt on every `up`; nothing in it is hand-edited. `data/secrets/` is never rewritten by `render`.

## Deployment migrations

`migrations/NNNN_<slug>.py`, applied in numeric order, once, recorded in `data/.neops/state.json`:

```json
{"schema": 1, "applied": [{"name": "0001_initial_layout", "at": "2026-09-14T10:00:00Z", "cli": "2.0.0"}]}
```

A migration is a module with `DESCRIPTION`, `IDEMPOTENT` (whether a crashed run may simply be re-run) and `apply(ctx)`. Before applying anything, `migrate` snapshots `state.json` and `.env` into `backups/pre-migrate-<ts>/`. A migration that fails leaves no entry in `applied`; on the next run it is re-run when `IDEMPOTENT`, otherwise `migrate` stops and names the migration and the snapshot. `install` and `up` refuse a `data/` whose state file was written by a newer CLI. `ctx` offers: `repo`, `data`, `env` (read, `set`, `rename`, `unset`, preserving comments and order), `move(src, dst)`, `mkdir`, `chown_via_container(path, uid, gid)` (a throwaway `docker run --rm -v … alpine chown`, so no sudo is needed), `compose(*args)` for the rare migration that needs a container, and `log`. Migrations run before containers start; one that needs the stack says so in its docstring and calls `ctx.compose` itself.

`0001_initial_layout`: creates the `data/` tree (including `secrets/` at 0700 and `elasticsearch/` owned by 1000:0) and the state file. Fresh installs and upgrades take the same path. Future examples: renaming an `.env` key, moving a data directory, a Postgres major upgrade (`pg_upgrade` in a helper container), a one-off `manage.py` fix.

App-internal migrations are untouched: `cms-init` runs Django's, the engine runs its own on boot, Keycloak migrates its schema itself.

## Security posture

- `.env` holds operator-chosen secrets (`NEOPS_CMS_DB_PASSWORD`, `NEOPS_ENGINE_DB_PASSWORD`, `NEOPS_KEYCLOAK_DB_PASSWORD`, `DJANGO_SECRET_KEY`, `NEOPS_ADMIN_PASSWORD`, `NEOPS_KEYCLOAK_ADMIN_PASSWORD`, `NEOPS_GRAFANA_ADMIN_PASSWORD`, `NEOPS_OIDC_CLIENT_SECRET`); `check` refuses blanks and placeholders (`changeme`, `unsafe`) and prints `openssl rand -hex 32`. Generated secrets are 0600 under `data/secrets/`.
- Base file publishes nothing; expose mode binds `127.0.0.1`; Traefik mode publishes only 80/443 (+ the monitor port in shared-host mode). The engine's worker API (`/blackboard`, `/workers`, `/function-blocks`) is never reachable from outside the compose network. Traefik dashboard off. No Docker socket in any container.
- The worker connects to devices without SSH host-key verification (SDK behaviour, not this repo's); it runs on the private network with no published port, which is the mitigation this design offers.
- Core: `DEBUG=False`, `CORS_ORIGIN_ALLOW_ALL` only when web and CMS origins differ, `DJANGO_ALLOWED_HOSTS` derived (never `*`), `SESSION_COOKIE_SECURE` defaults on. Engine: `NEOPS_AUTHZ_MODE=enforce`, `NODE_ENV=production`.
- Superuser password comes from `.env`, set only on creation (chart semantics).
- Secret rotation only through `./neops rotate <what>`; editing a password in `.env` by hand is detected by `check` and named. Backups are credentials and are stored 0600 in a 0700 directory.

## Verification

- **Unit tests** (`uv run pytest`): env parsing and validation; URL → Traefik model for hosts and shared-host mode; scenario and URL rules; migration ordering, idempotency and state; secrets generation (SANs, permissions, stale-SAN detection); a test that parses every compose file and asserts no top-level named volume, every bind mount under `${NEOPS_DATA_DIR}`, `./certs`, `./cust-cert`, `./generated`, `./metrics`, and no `${}` reference to a key that only exists in a generated env file.
- **Config gate**: `docker compose config` for every `examples/*.env` (with dummy secrets), in `make check` and in CI.
- **End-to-end** on this box, per scenario, each in a fresh clone directory with the port variables set: `install` from the example `.env` → `doctor` green → GraphQL `login` returns a token → engine `/version` and the worker registered with every base function block the image ships (22 at `0.2.0-beta.5`; the test counts them from the image rather than hardcoding) → monitor `/config.js` carries the right URLs → web client index loads. Keycloak scenario adds a full browser login through Playwright (create a user via the Keycloak admin API, log in, land on the web client with a session). Shared-host scenario checks admin, graphiql static assets, and the OIDC callback path all reach core.
- **Chaos**: `POST <NEOPS_ENGINE_URL>/blackboard/job` from outside returns 403 while the worker still polls; `docker kill` each service and confirm it comes back healthy; `docker system prune -a --volumes` while stopped, then `./neops up`, then re-run the e2e assertions and confirm the previously issued API key and a device created before the prune still exist; run `install` twice and confirm exactly one API key row exists; rotate each secret and confirm the stack stays healthy; corrupt `.env` (blank secret, bad URL, incompatible overlays) and confirm `check` blocks with the right message; engine restarted while the worker is polling.
- **Design challenge**: done, two reviewer agents (ops/security; compose/Traefik/Keycloak/Django). Implementation agents (Tier 2/3) run the per-scenario e2e and chaos suites in parallel during the build.

## Open verifications (resolved during implementation, each has a fallback)

1. Shared-host mode: does core's SPA catch-all or the web client claim any path the other needs beyond the prefix list in `routes.py`? Checked in the e2e run (admin, graphiql, `/auth/callback`, `/login`, deep links). Fallback: extend the list.
2. Does editing `data/secrets/engine.env` alone make `up` recreate the engine? Likely yes (the resolved value is part of the service config hash) but unverified; `token` recreates explicitly regardless.
3. The exact engine prefixes the monitor app calls (allow-list): derived from `rest/monitor-app/src/lib/api` at implementation and confirmed by the Playwright run.
4. Does the published `neops-worker-sdk:0.2.0-beta.5` image carry `neops_workflow_engine_client==0.43.0-beta.2`? (Source pin matches; image not inspected.)
5. `neops-monitor-app` tag availability: pinned to the engine tag; tested with a local build until the engine's release job is fixed and a new tag is published.

Resolved during the challenge round: `up --wait` with the one-shot works on Compose 5.4 (verified); the Keycloak healthcheck form is the documented `/dev/tcp` one; `--root-path` is not used; the legacy `oidc-config.json` is not needed.
